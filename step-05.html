Why Multiservice?

WAF++ is not a monorepo and not a single application. It is a federation of focused repositories — each with its own lifecycle, technology, and team — held together by one data contract and one API.

🧩 Not a monorepo — an umbrella of repos

The root folder that contains all repositories is only a convenience. It gives you a single place to open your editor and run cross-repo searches, but it does not make WAF++ a monorepo.

  • Every component is an independent git repository.
  • Each repository has its own version, CI/CD pipeline, and release cycle.
  • There is no shared lockfile, shared build system, or shared package manager workspace.
  • The repositories are grouped in one folder because they solve one problem domain together.

🎯 Why separate repositories?

Splitting the ecosystem into independent repos was a deliberate architectural choice.

  • Clear ownership — a small team can own, build, and release one component without touching the others.
  • Independent versioning — wafpass-core can ship v1.1.3 while wafpass-dashboard stays on v1.1.0.
  • Technology freedom — Python for the engine and server, TypeScript/React for the UI, Ruby/Jekyll for the website.
  • Isolation — a broken dashboard release cannot block a security fix in the engine.
  • Reusability — wafpass-core can be installed and used without the server or dashboard.

🧱 Why separate services?

Each runtime component has a single, well-defined responsibility.

  • pass — parses IaC and evaluates controls (stateless compute).
  • wafpass-server — owns persistence, auth, and business logic.
  • wafpass-dashboard — renders the user interface and talks only to the server.
  • wafpass-mcp — translates the server API into MCP tools for AI clients.
  • wafpass-action — wraps the engine for CI/CD without owning its code.

This keeps failure domains small and lets each service scale where it matters.

🔗 What holds it together?

Two contracts replace a single codebase:

wafpass-result.json

The central result schema emitted by the engine and consumed by the server, dashboard, MCP bridge, PDF reporter, and observability exports.

/api/v1

The versioned REST API surface of wafpass-server. Every downstream tool reads and writes through this contract.

🚀 Build and release cadence

  • Each repo releases when it is ready — no coordinated “big bang” cut.
  • PyPI packages, Docker images, npm builds, and GitHub Action tags live in their own repositories.
  • Cross-cutting changes are coordinated through ADRs and the shared result schema version.

⚠️ Consequences for onboarding

  • You clone several repositories, not one.
  • You run each component from its own directory.
  • There is no root-level orchestration file; per-repo READMEs are the source of truth.
  • Changes that touch the result contract need extra care because multiple repos depend on it.
