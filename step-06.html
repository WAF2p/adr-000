The wafpass-result.json Contract

Every integration in WAF++ speaks the same language: wafpass-result.json. It is the single source of truth between the engine, the server, the dashboard, AI assistants, CI pipelines, and export formats.

🤝 Producer and consumer diagram

The contract decouples producers from consumers. As long as a result file validates against the schema, any tool can read or write it without knowing the internals of the other repositories.

📄 Annotated wafpass-result.json example

The snippet below is a realistic, but not exhaustive, result file. Every key is followed by an inline explanation so you can read the file once and understand what each section is for. In real output the comments are not part of the JSON; they are shown here for teaching. 

{
  // Schema contract version. Consumers reject files whose major version they do not understand.
  "version": "1.0.0",

  // Who produced this file, which engine build, and what inputs were scanned.
  "generator": {
    "name": "wafpass-core",
    "version": "2.4.1",
    "commit": "a1b2c3d"
  },

  // Everything that identifies this scan run.
  "run": {
    "id": "0192e6c4-0000-7000-8000-000000000001",  // Stable UUID used by /api/v1/runs/{id}
    "project": "billing-service",                    // Logical project name in the server
    "stage": "prod",                                 // Environment: local | staging | prod
    "started_at": "2026-09-17T12:00:00Z",            // ISO-8601 UTC; drives sorting and reports
    "duration_ms": 1240,                             // Total time from config load to report write
    "iac_framework": "terraform",                    // terraform | cdk | pulumi | bicep
    "working_dir": "modules/billing",                // Relative path that was scanned
    "config": {                                      // Engine configuration used for this run
      "control_filter": ["SEC-*", "OPS-*"],
      "severity_threshold": "medium",
      "include_passed": false
    }
  },

  // Roll-up numbers every dashboard, badge, and CI gate reads first.
  "summary": {
    "total": 87,        // Controls evaluated (not the number of resources)
    "passed": 72,       // Controls that met the requirement
    "failed": 12,       // Controls that did not
    "skipped": 3,       // Controls excluded by scope, waivers, or filters
    "score": 82.8,      // 0-100 compliance score; optional, dashboard uses it for charts
    "severities": {     // Drill-down used by the dashboard and Slack/Jira exporters
      "critical": 1,
      "high": 4,
      "medium": 5,
      "low": 2,
      "info": 0
    }
  },

  // One object per failed or skipped finding. Passed findings are optional.
  "findings": [
    {
      "control_id": "SEC-001",                       // Matches the framework control ID exactly
      "pillar": "Security",                            // Governance pillar (Security, Operations, ...)
      "severity": "high",                              // critical | high | medium | low | info
      "resource": "aws_s3_bucket.data",                // Terraform/CDK resource address
      "resource_type": "aws_s3_bucket",                // Resource type for grouping and trend charts
      "file": "infra/s3.tf",                           // Source file, relative to working_dir
      "line": 42,                                      // Approximate line number for IDE links
      "column": 5,
      "message": "S3 bucket is missing server-side encryption configuration.",
      "remediation": "Add aws_s3_bucket_server_side_encryption_configuration ...",
      "references": [                                  // Links to framework docs and external guidance
        "https://adr-000.waf2p.dev/controls/SEC-001",
        "https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-encryption.html"
      ],
      "waived": false,                                 // True if a waiver was applied
      "evidence": {                                    // Optional: snippets, hashes, or snapshots
        "code_snippet": "resource \"aws_s3_bucket\" \"data\" { ... }",
        "fingerprint": "sha256:..."
      }
    }
  ],

  // Optional: waivers, risks, and metadata that the server stores as JSONB.
  "waivers": [],
  "risks": [],
  "metadata": {
    "ci_run_url": "https://github.com/WAF2p/billing/actions/runs/12345",
    "git": {
      "branch": "main",
      "commit": "deadbeef",
      "dirty": false
    }
  }
}

Top-level envelope

version, generator, run, and summary are always present. They let consumers decide whether they can parse the file and how urgent it is.

Run identity

run.id becomes the primary key on the server. run.project + run.stage group runs in dashboards and passports.

Summary math

total = passed + failed + skipped. Severities are independent: one control failure may or may not have a severity depending on the control.

Findings are the payload

Each finding is self-contained: a control, a resource, a location, a message, and optionally remediation links and evidence. This is what PDF/SARIF/Slack exporters render.

Optional sections

waivers, risks, and metadata are not required for a valid result, but they make the file richer for audits, evidence packages, and CI links.

Security note

No secrets, state files, or raw plan output ever belong in this file. Only resource addresses, code snippets, and findings. Sensitive data goes to the secure evidence store.

🎯 Why one central result file?

  • Decoupling: The dashboard does not need to know how Terraform is parsed.
  • Reproducibility: Save a result and re-run the same report months later.
  • Auditability: Immutable evidence packages are built from result JSON.
  • Testability: Fixtures are plain JSON; every consumer can have contract tests.
  • Portability: Move a scan from CI to server to dashboard without re-running it.

🔢 Versioning rules

  • Major bump when required fields change or a field is removed.
  • Minor bump when new optional fields are added.
  • Patch bump for documentation or formatting changes only.
  • Consumers must reject unknown major versions and warn on unknown minors.
  • The engine, server, and dashboard release notes always mention schema version changes.

🛠️ Validating and working with results

# Validate a result against the schema
wafpass validate wafpass-result.json

# Push to the server
wafpass push wafpass-result.json --server http://localhost:8000/api/v1

# Convert to SARIF for other tools
wafpass report --input wafpass-result.json --format sarif

# Server stores the raw JSONB and exposes it at /api/v1/runs/{id}
curl http://localhost:8000/api/v1/runs/0192e6c4-... \
  -H "Authorization: Bearer $WAFPASS_API_KEY"
