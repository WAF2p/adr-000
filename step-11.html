Integrations

WAF++ plugs into the tools developers already use: CI pipelines, AI assistants, chatops, and observability platforms. This step covers how each integration is built, tested, and extended.

🧰 Shared integration philosophy

  • Every integration consumes or produces the same wafpass-result.json contract.
  • Integrations do not duplicate engine logic; they orchestrate wafpass-core via CLI, API, or library calls.
  • Secrets and credentials stay in the host platform (GitHub secrets, environment variables, key vaults).
  • Each integration has its own repository with independent versioning and release cycle.
  • Releases follow semantic versioning and publish artefacts (Docker images, GitHub releases, npm/pypi packages).

🔧 wafpass-action — GitHub Action

Composite GitHub Action for CI/CD scans and PR annotations.

https://github.com/WAF2p/wafpass-action
Open wafpass-action repo

A composite/action-type repository that runs wafpass check in GitHub Actions, posts PR annotations, and optionally pushes results to wafpass-server.

Repository layout

wafpass-action/
├── action.yml              # GitHub Action inputs, outputs, runs
├── README.md               # Usage examples and marketplace listing
├── scripts/
│   ├── entrypoint.sh       # Setup, scan, report
│   └── annotate.py         # Convert findings to GitHub PR annotations
├── tests/
│   ├── test_annotate.py
│   └── fixtures/
└── .github/workflows/
    └── ci.yml              # Self-test the action on every PR

Technology choices

Composite Action

Keeps the action portable and avoids a custom Docker image unless needed.

Python 3.11+

Annotation formatting and result normalisation in a small Python helper.

GitHub API

Creates check-runs, PR annotations, and job summaries via GITHUB_TOKEN.

shell scripting

Bash glue for installing wafpass-core and invoking the CLI.

Code style & guidelines

  • Shell scripts pass shellcheck with no warnings.
  • Python helper code follows the same ruff/black rules as wafpass-core.
  • Inputs are validated early; fail the step with a clear message if required inputs are missing.
  • Never log secrets; mask API keys and tokens before printing.
  • Tag releases as v1.2.3 and update the floating major tag (v1) for non-breaking releases.

Example workflow usage

# .github/workflows/wafpass.yml in a consumer repo
name: WAF++ Scan
on: [pull_request, push]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: waf2p/wafpass-action@v1
        with:
          iac: terraform
          path: ./infra
          fail-on-severity: high
          push-to-server: true
          server-url: https://wafpass.example.com/api/v1/runs
          api-key: ${{ secrets.WAFPASS_API_KEY }}

Developer onboarding

  1. Fork/clone wafpass-action.
  2. Run shellcheck scripts/*.sh and the Python test suite.
  3. Test the action in a personal repository using a local branch reference.
  4. Update action.yml metadata and README.md when adding inputs.
  5. Open a PR; the repo's own CI will exercise the action end-to-end.

🤖 wafpass-mcp — Model Context Protocol server

MCP bridge exposing WAF++ data to AI assistants and IDEs.

https://github.com/WAF2p/wafpass-mcp
Open wafpass-mcp repo

Exposes WAF++ scan data and controls as tools to AI assistants (Claude Desktop, IDEs, and other MCP clients). Users can ask questions like "Which Security controls failed in the last run?" or "Summarise the Cost findings."

Repository layout

wafpass-mcp/
├── src/
│   ├── index.ts              # MCP server entry and transport
│   ├── server.ts             # Tool definitions and handlers
│   ├── tools/
│   │   ├── listRuns.ts
│   │   ├── getRun.ts
│   │   ├── summariseFindings.ts
│   │   └── listControls.ts
│   ├── api.ts                # wafpass-server REST client
│   └── types.ts              # Shared TypeScript types
├── tests/
│   └── tools.test.ts
├── package.json
├── tsconfig.json
└── README.md

Technology choices

TypeScript / Node.js 20+

MCP SDK is TypeScript-first; strict type safety across tool schemas.

MCP SDK

Implements stdio and SSE transports, tool registration, and schema validation.

Zod

Defines tool argument schemas; errors are surfaced to the AI client clearly.

Axios

HTTP client for the wafpass-server REST API.

Code style & guidelines

  • Formatter: prettier; Linter: eslint with TypeScript strict.
  • Each tool must declare a clear name, description, and Zod parameter schema.
  • Tool handlers return structured text; include Markdown tables for findings when useful.
  • Never expose raw API keys in tool responses; the server uses them internally only.
  • Handle MCP client lifecycle events (initialize, shutdown) gracefully.

Example tool skeleton

// src/tools/getRun.ts
import { z } from 'zod';
import { api } from '../api';

export const name = 'wafpass_get_run';

export const description =
  'Retrieve a single WAF++ scan run by ID, including all findings.';

export const parameters = z.object({
  run_id: z.string().uuid().describe('The run UUID'),
});

export async function handler(args: z.infer<typeof parameters>) {
  const run = await api.get(`/runs/${args.run_id}`);
  return {
    content: [
      {
        type: 'text',
        text: `# Run ${run.data.run_id}\n\n` +
          `- Project: ${run.data.project_id}\n` +
          `- Findings: ${run.data.findings_count}\n\n` +
          run.data.findings.map((f: any) => `- ${f.control_id}: ${f.title}`).join('\n'),
      },
    ],
  };
}

Developer onboarding

  1. Clone wafpass-mcp and install dependencies.
  2. Configure a local MCP client (Claude Desktop config) pointing at your dev build.
  3. Add a tool in src/tools/, register it in server.ts, and add tests.
  4. Test the conversation flow end-to-end with the MCP inspector.
  5. Update the README with example prompts that exercise your new tool.

🌐 Webhooks and observability exporters

The server can dispatch scan results to external systems. New exporters live either in wafpass-core (CLI-time) or in wafpass-server (server-time). Choose based on whether the export should happen in CI or after ingestion.

  • CLI exporters: run during wafpass check. Examples: Slack, Datadog, Splunk, Grafana annotations.
  • Server exporters: trigger after a result is stored. Examples: outbound webhooks, email digest, ticket creation.
  • Retry policy: exponential backoff with a dead-letter queue for failed webhooks.
# Example server webhook payload
{
  "event": "run.completed",
  "run_id": "0192e6c4-...",
  "project_id": "my-project",

  },
  "url": "https://dashboard.example.com/runs/0192e6c4-..."
}

🧪 Testing strategy for integrations

  1. Unit tests: helper scripts, formatters, and tool handlers in isolation.
  2. Mocked external APIs: use nock (JS) or responses/httpx mocks (Python) for GitHub API and wafpass-server calls.
  3. Integration tests: run the GitHub Action in a test repo or the MCP server with the MCP inspector.
  4. Contract tests: verify produced payloads still match the receiver's schema.

🚀 Integration developer onboarding flow

  1. Pick the integration type (GitHub Action, MCP tool, exporter, or new platform).
  2. Read the relevant repo README and run its local test suite.
  3. Read the wafpass-result.json schema to know what fields are available.
  4. Implement the smallest useful feature: one action input, one MCP tool, or one exporter.
  5. Add tests and documentation; follow the release/versioning rules.

🔒 Security & trust assumptions

  • Integrations must treat API keys and tokens as sensitive; mask them in logs and store them only in the host platform's secret manager.
  • MCP servers receive arbitrary natural-language instructions; validate tool arguments strictly and return minimal data by default.
  • GitHub Action inputs that accept paths must reject traversal patterns.
  • Webhook receivers should verify signatures or shared secrets when available.
