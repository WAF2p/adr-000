🧰 One toolchain for every repository: mise

All repositories in the WAF++ umbrella use mise (formerly rtx) to declare their language runtimes and local tools. Instead of managing Python, Node, Ruby, and Task versions yourself, you install one tool and let each repo’s mise.toml provide the rest. 

# 1. Install mise once (macOS/Linux example)
curl https://mise.run | sh
# or via Homebrew: brew install mise

# 2. Clone the umbrella and enter a repo
mkdir waf++&amp;&amp; cd waf++
for repo in framework framework-en waf2p.github.io wafpass-core wafpass-server wafpass-dashboard wafpass-mcp wafpass-action; do
  case $repo in
    framework)      git clone --single-branch --branch main-de https://github.com/WAF2p/framework.git $repo ;;
    framework-en)   git clone --single-branch --branch main-en https://github.com/WAF2p/framework.git $repo ;;
    *)              git clone https://github.com/WAF2p/${repo}.git $repo ;;
  esac
done

# 3. Trust the repo-local tool definitions and install what it needs
cd wafpass-core
mise trust
mise install        # downloads Python 3.11, ruff, mypy, etc.

# 4. Run the quality gates exactly as CI does
mise run lint
mise run test

What a typical mise.toml in a Python repo looks like:

[tools]
python = "3.11"
uv = "latest"
"pipx:task" = "latest"
"pipx:ruff" = "latest"
"pipx:mypy" = "latest"
"pipx:pytest" = "latest"

[env]
_.python.venv = { path = ".venv", create = true }
WAFPASS_LOG_FORMAT = "text"

[tasks.lint]
description = "Run ruff and mypy"
run = "ruff check src tests && ruff format --check src tests && mypy src"

[tasks.test]
description = "Run pytest"
run = "pytest"

[tasks.dev]
description = "Editable install"
run = "uv pip install -e .[dev]"

Why mise?

One installer, per-repo pinned versions, automatic venv activation, and task aliases that match CI. New contributors are productive in minutes instead of hours.

What it installs per repo

wafpass-core/server/mcp/action: Python, uv, ruff, mypy, pytest, Task. wafpass-dashboard: Node LTS, pnpm, vitest. waf2p.github.io: Node, Ruby, Jekyll, Antora. framework: Ruby/Antora optional for local preview.

Tasks are the contract with CI

GitHub Actions calls mise run lint and mise run test, so local verification and CI use identical commands and versions.

Migration from manual setups

If you already have Python/Node installed, mise still creates the project’s isolated venv and installs the pinned tools. Your global installation is left untouched.

🚀 Run the local stack

There is no umbrella docker-compose.yml in this ADR. Start each component from its own directory after mise install:

# 1. Start PostgreSQL and wafpass-server
cd wafpass-server
mise run dev          # uv pip install -e .[dev] + alembic upgrade head + uvicorn --reload

# 2. In another terminal, start the dashboard
cd ../wafpass-dashboard
mise install
mise run dev          # npm/pnpm install + vite dev

# 3. Run a scan and push it to the server
cd ../wafpass-core
mise run dev
wafpass check ./dummy_code --output json \
  --push http://localhost:8000/api/v1/runs --api-key key

See each repo's README.md and mise.toml for exact environment variables and ports.

✅ Onboarding checklist

  • Read this ADR (ADR-000).
  • Start wafpass-server and wafpass-dashboard locally by following their README.md files.
  • Open the dashboard and log in with the seeded admin account.
  • Run wafpass check ./dummy_code --summary from the wafpass-core repo to see the CLI in action.
  • Push a result to the local server and view it in the dashboard.
  • Read the per-repo README.md and TECH.md / AGENTS.md for the component you will work on.
  • For docs work: run task site:serve in waf2p.github.io and edit .adoc files in framework (branch main-de) / framework-en (branch main-en).
  • For AI/MCP work: follow wafpass-mcp/README.md to connect Claude Desktop.

📜 Conventions & decisions

  1. Single result schema: wafpass-result.json is the only contract between engine, server, dashboard, and exports.
  2. Versioned API: all server endpoints live under /api/v1; unversioned paths were removed.
  3. Monorepo-ish layout: each component is a separate git repo under a common umbrella directory; there is no shared orchestration file in this ADR.
  4. Docs separate from site: framework content lives in framework / framework-en (same repository, branches main-de / main-en); the website consumes them as Antora sources.
  5. Controls as data: WAF++ controls are YAML files, updated independently of the engine.
  6. SSO-ready: the server supports OIDC/SAML2 SSO; production brings its own IdP.
  7. Exclusion policy: demo, validation, UI widget, and AI-tooling folders are kept out of the core architecture ADR.
